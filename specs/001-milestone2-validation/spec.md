# Feature Specification: Milestone 2 Validation (False Positive Rates)

**Feature Branch**: `001-milestone2-validation`  
**Created**: 2026-03-27  
**Status**: Draft  
**Input**: User description: "Verify v0.1 alert results and report false positive rate"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Retrieve Alert History (Priority: P1)

As a security researcher (Member D), I want to retrieve all historical alerts generated by the v0.1 algorithms (e.g., Z-Score, Whale Alert) from the database so that I can have a dataset to verify.

**Why this priority**: Essential first step. Without the generated alerts, there is nothing to verify.

**Independent Test**: Can be tested by querying the PostgreSQL database for the `anomalies` table and ensuring events are correctly returned for a given market slug.

**Acceptance Scenarios**:

1. **Given** the core_analysis algorithm has written v0.1 anomalies to the database, **When** I query the DB via `query_anomalies(slug)`, **Then** I receive a list of timestamped anomaly events.

---

### User Story 2 - Manual & Semi-Automated Verification (Priority: P1)

As a security researcher, I want to cross-reference each alert with public news events and on-chain explorer data to determine if the alert represents true market manipulation or a normal market reaction to external events.

**Why this priority**: Core of Milestone 2. We must differentiate true positives from false positives.

**Independent Test**: Can be tested by selecting 10 historical alerts and successfully labeling them as TRUE_POSITIVE or FALSE_POSITIVE based on external data.

**Acceptance Scenarios**:

1. **Given** an alert indicating a sudden price spike, **When** I look up the timeline for major news regarding that market, **Then** I label the alert as FALSE_POSITIVE if justified by a major news drop.
2. **Given** an alert with no correlating external news, **When** I analyze the transaction flow, **Then** I label the alert as a potential TRUE_POSITIVE.

---

### User Story 3 - False Positive Feedback Report (Priority: P2)

As a security researcher, I want to calculate the false positive rate for v0.1 algorithms and provide feedback to the Core Algorithm Engineer (Member C) to adjust detection thresholds.

**Why this priority**: Closes the feedback loop for Milestone 2 MVP. Required to get the +5% Spec-Driven Bonus.

**Independent Test**: Can be tested by generating a markdown report summarizing the total alerts, number of verified false positives, and the calculated FP rate.

**Acceptance Scenarios**:

1. **Given** a fully labeled dataset of alerts, **When** I run the reporting script, **Then** a feedback report (e.g., `v0.1_false_positive_report.md`) is generated.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST allow retrieving anomaly records from the PolyWatch database by time window and market.
- **FR-002**: Researcher MUST establish a repeatable process (manual or automated) to assign a label (TP/FP) to an anomaly event.
- **FR-003**: System MUST output a quantifiable False Positive Rate (e.g., FP Rate = False Positives / Total Alerts).

### Key Entities

- **Anomaly Event**: An event in the DB triggered by v0.1 algorithms, containing timestamp, market slug, type (e.g., zscore_spike), and severity.
- **Verification Label**: A boolean or categorical tag attached to an Anomaly Event during Member D's verification phase.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: At least 50 v0.1 alerts (or all alerts if < 50) verified and labeled.
- **SC-002**: A concrete False Positive Rate percentage is computed and documented.
- **SC-003**: Feedback report delivered to Member C detailing common reasons for false positives (e.g., "News-driven volatility not currently filtered").
- **SC-004**: Milestone 2 artifacts (`forensics/alerts_to_verify.csv`, `forensics/v0.1_false_positive_report.md`) are explicitly referenced and summarized in `forensics/Individual-Evidence-Pack-Milestone3.md` for final submission.

## Assumptions

- The `data_pipeline` is running and has populated the DB.
- `core_analysis` (Member C) has successfully run v0.1 algorithms over the dataset.
- Real-world news timelines for the analyzed markets are accessible.
